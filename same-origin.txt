What you are experiencing with LinkedIn is the core design of web browser security and session management.

When you open a new tab and go to LinkedIn, the browser doesn't send a explicit message saying *"Hey, Tab 2, copy Tab 1's memory!"* Instead, it relies on foundational web mechanisms.

---

## 1. What is this concept called?

This concept relies on two core principles:

1. **The Same-Origin Policy (SOP):** A fundamental web security architecture. It states that any two tabs running on the same **Origin** (e.g., `[https://linkedin.com](https://linkedin.com)`) share access to client-side storage mechanisms (like `Cookies` and `localStorage`).
2. **Ambient Authority / Automatic Credential Delivery:** When you open `linkedin.com` in a new tab, the browser automatically attaches all non-expired cookies tied to `linkedin.com` in the HTTP request headers.

---

## 2. How it works under the hood

When you log in to LinkedIn:

1. **Authentication:** You submit your username and password.
2. **Cookie Issuance:** LinkedIn's backend validates your credentials and responds with a HTTP response header:
```http
Set-Cookie: li_at=eyJhbGciOi...; Domain=.linkedin.com; Path=/; Secure; HttpOnly; SameSite=Lax

```


3. **Browser Storage:** The browser saves this cookie (`li_at` is LinkedIn’s primary auth token) under the `linkedin.com` domain storage sandbox.
4. **New Tab Request:** When you open a fresh tab and navigate to `linkedin.com`, the browser checks its cookie store for `linkedin.com`. It finds `li_at` and automatically attaches it to the HTTP GET request:
```http
Cookie: li_at=eyJhbGciOi...

```


5. **Session Resolution:** LinkedIn’s backend receives the request, sees `li_at`, validates it, and renders your personalized feed—all before the page even finishes loading on the frontend.

---

## 3. How to implement this in your project

Depending on whether you are building a **SSR/Traditional Backend app** or a **Single Page Application (SPA)**, here are the standard patterns:

### Method A: HTTP-Only Cookies (Best Practice & What LinkedIn Uses)

If you store session IDs or JWTs in `HttpOnly` cookies, the browser handles multi-tab synchronization **100% automatically**.

```javascript
// Backend (Node.js / Express Example)
app.post('/api/login', (req, res) => {
  // 1. Authenticate user...
  const token = generateAuthToken(user);

  // 2. Set as secure cookie
  res.cookie('session_token', token, {
    httpOnly: true, // Prevents XSS script attacks from reading the token
    secure: true,   // Transmitted only over HTTPS
    sameSite: 'lax', // CSRF protection
    maxAge: 7 * 24 * 60 * 60 * 1000 // 7 days
  });

  res.json({ success: true });
});

```

* **Why this works across tabs:** Every new tab opened to your domain automatically sends `session_token` with initial page loads and API requests.

---

### Method B: `localStorage` (For SPAs using Authorization Headers)

If you store JWT tokens in `localStorage` instead of cookies, all tabs on the same domain share that `localStorage` object.

```javascript
// Tab 1 (Login Page):
async function handleLogin() {
  const res = await fetch('/api/login', { method: 'POST', body: credentials });
  const { token } = await res.json();
  
  // Stored across all current and future tabs of this domain
  localStorage.setItem('auth_token', token); 
}

// Tab 2 (App Load):
function initializeApp() {
  const token = localStorage.getItem('auth_token');
  
  if (token) {
    // User is logged in! Attach to headers
    fetchUserData(token);
  } else {
    // Redirect to login
    window.location.href = '/login';
  }
}

```

---

### Method C: Real-Time Tab Synchronization with `storage` Events or `BroadcastChannel`

If you want tabs to instantly know when a user logs in or logs out in **another** tab without needing a page refresh, you can synchronize them live using native APIs.

#### Option 1: Storage Event (Native `localStorage` listener)

The `storage` event fires in **all other tabs** on the same origin when `localStorage` changes:

```javascript
// Put this in your main application initialization script
window.addEventListener('storage', (event) => {
  if (event.key === 'auth_token') {
    if (!event.newValue) {
      // Token was deleted in another tab (User logged out)
      console.log('User logged out in another tab. Redirecting...');
      window.location.href = '/login';
    } else {
      // Token was set in another tab (User logged in)
      console.log('User logged in in another tab. Refreshing session...');
      window.location.reload();
    }
  }
});

```

#### Option 2: `BroadcastChannel` API

For modern web apps, the `BroadcastChannel` API allows direct pub/sub communication between tabs:

```javascript
// Create a shared channel across tabs
const authChannel = new BroadcastChannel('auth_status');

// Tab 1 (Trigger on Logout):
function logout() {
  localStorage.removeItem('auth_token');
  authChannel.postMessage({ type: 'LOGOUT' });
  window.location.href = '/login';
}

// Tab 2 (Listen for updates):
authChannel.onmessage = (event) => {
  if (event.data.type === 'LOGOUT') {
    alert('Logged out from another tab.');
    window.location.href = '/login';
  }
};

```

## ⚠️ Important Considerations for Exposing LinkedIn Tokens

If your specific scenario involves trying to access or extract an **actual LinkedIn session token** (`li_at`) to programmatically perform actions:

1. **Security Vulnerability:** Exposing session cookies via non-`HttpOnly` channels or passing them outside the official browser context opens up risks for Cross-Site Scripting (XSS) or token hijacking.
2. **LinkedIn Anti-Scraping / Terms of Service:** LinkedIn enforces strict token checks, fingerprinting (matching IP, User-Agent, and SSL signatures), and automated behavior detection. Sharing `li_at` cookies across servers or headless browsers will quickly trigger security checkpoints, CAPTCHAs, or account restrictions.
3. **Official Alternative:** If you need to authenticate users via LinkedIn in a custom app, use **LinkedIn OAuth 2.0** (`Sign In with LinkedIn`), which yields an authorized API access token safely designed for backend calls rather than sharing raw browser session cookies.
